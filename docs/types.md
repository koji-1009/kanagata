# Generated types

- Every schema in `components.schemas` is a named type (`export type User = { … }`), referenced by name. Names are PascalCase, with `_` before one that would start with a digit, and `_` for one with no letter or digit (`-`); a taken or reserved name gets a number (`User2`). `export interface schemas` maps each original name to its type.
- Operations are `paths[path][method]`, `webhooks[name][method]` (3.1 and 3.2; see [Webhooks](#webhooks)), an operation's `callbacks[name][expression][method]` (see [Callbacks](#callbacks)), and `operations[operationId]`. An Operation Object reached again through a Path Item that two paths share (a `$ref` or a YAML alias) is declared once there; one with an `operationId` reached again where its type differs (a YAML alias of the Operation Object under paths with different path-level parameters; a path's and a webhook's, see [Webhooks](#webhooks)) is an error, since `operations[operationId]` has one type. Another Operation Object with the same `operationId`, which OpenAPI requires to be unique, is an error, even when written alike. The methods are the Path Item's fields in OpenAPI's order (`get` … `trace`, then `query`), then the keys of `additionalOperations` (3.2) as written (`COPY`). A key that is a fixed field's method (`POST`), which OpenAPI forbids, or its name (`post`) is an error; methods are case-sensitive, so `Patch` is another method. The fields OpenAPI 3.2 adds (`$self`, `query`, `additionalOperations`, `in: querystring`, a `$ref` as a media type, `itemSchema`) are read in 3.2 documents only.
- A parameter defined by `content` is the schema of its media type for `application/x-www-form-urlencoded`, which the client encodes as it does any parameter, and `string` for any other: the client has no document to serialize the value by, so the call passes the serialized text (`filter: JSON.stringify({ q: "a" })` for `application/json`). A response header defined by `content` keeps the schema.
- An `in: querystring` parameter (3.2) is `parameters.querystring`, without its name, which is not sent; it is defined by `content`, so it is typed as above.
- A schema with a `readOnly` / `writeOnly` property (on it or on a schema it references) gets a second type for what is sent to the API (a path's request, a webhook's responses), `UserInput`.
- A property left out of a view is left out of the whole schema it is in, whatever else lists it: a `required` next to it, next to its `$ref` (3.1, 3.2) or in an `allOf` / `oneOf` / `anyOf` member does not bring it back (`required` takes effect on the other side only, as OpenAPI says). A `$ref` to a schema with the property is written out without it, since the reference's view has it, whatever keywords are next to the `$ref`: `allOf: [{ $ref: Base }, { properties: { id: { readOnly: true } } }]`, `allOf: [{ $ref: Base, required: [name] }, …]` and `{ $ref: Base, properties: { id: { readOnly: true } } }` (3.1, 3.2) send Base's properties but `id`.
- The `description` and `deprecated` of schemas, properties, operations, parameters, request bodies and headers become JSDoc; a response's and a path item's are not read. In 3.1 and 3.2, a `description` next to the `$ref` to a parameter, request body or header replaces the referenced one's, as OpenAPI says; 3.0 ignores a Reference Object's other fields.
- A path parameter is required whatever its `required` says (OpenAPI requires it to be `true`): the path cannot be built without it. Other parameters, request bodies and headers are required where `required` is `true`.
- Header parameters named `Accept`, `Content-Type` or `Authorization`, and a response header `Content-Type`, are ignored, as OpenAPI requires.
- A field OpenAPI requires is an error where it is missing: a parameter's `name` and `in`, a parameter's or header's `schema` or `content` (one of the two, and `content` with exactly one media type, as OpenAPI requires), a request body's `content` (an empty one describes no representation, so it is `content: {}`, which no body matches), a server's `url`, and a path parameter for each template expression in a path (`{org}` in `/orgs/{org}`), which the call fills in. So is a path item, operation, parameter, request body, response, header, media type, `responses`, `headers` or `content` that is not an object, `parameters` or `servers` that is not an array, an `operationId` that is not a string, and a `required` that is not a boolean. These are checked where kanagata reads the field, so not in what it leaves out: a webhook's `servers`, a path item's `servers` next to an operation's own, a `requestBody` on a path's GET or HEAD.
- A parameter whose `in` is none of `path`, `query`, `header` and `cookie` (and `querystring` in 3.2) is left out.
- The `servers` of a path's operation, or of its path item, are `servers: ["https://uploads.example.com"]` in its type. A variable (`{region}`) is the values its `enum` lists, any string without one: `` `https://${"us" | "eu"}.example.com` ``. A relative URL resolves against where the document is served, which the types do not know, so it is any URL that ends as it does: `/v2` is `` `${string}/v2` ``. The call's `baseUrl` is offered these and takes any URL, since a deployment can serve the operation elsewhere (see [client.md](client.md#details)). The document's own `servers` are not read: the client's `baseUrl` names where it sends.
- A `requestBody` on a path's GET or HEAD operation is left out: fetch cannot send one (and OpenAPI 3.0 has consumers ignore it). A required one is left out with a warning, since no call is the request it asks for.
- A `requestBody` on DELETE is kept, in 3.0 too, although OpenAPI 3.0 has consumers ignore a body where HTTP leaves its meaning open (3.0.4 names DELETE): fetch sends it, 3.1 permits it (while advising against it), and APIs require one (GitHub's, in its 3.0 description as in its 3.1 one), whose calls could not be made without it.

## Webhooks

A webhook (`webhooks`, 3.1 and 3.2) is a request the API sends to a receiver the API consumer implements, and the responses the API expects back. `webhooks` is read in 3.1 and 3.2 documents only: it is no field of OpenAPI 3.0. A webhook's types are a path operation's with the directions swapped:

- Its parameters and request body are the read view, and its responses (headers and content) the write view: `readOnly` properties are kept and `writeOnly` ones left out of the request, the other way round in the responses, so a schema with either is `User` in the request and `UserInput` in the responses.
- A form, in its request or its responses, is its schema: the client does not receive it, so it is not the text a path's form response is.
- It keeps a `requestBody` on GET and HEAD, since the API sends the request.
- It has no `servers`: the API sends its request, so there is none to choose.
- Every key of `webhooks` is a name, `x-` ones included.
- An operation with an `operationId` that is both a path's and a webhook's (in a Path Item they share) is an error where its two types are declared differently, as they are when it has a `readOnly` / `writeOnly` property or refers to a schema with one (`User` in one, `UserInput` in the other): `operations[operationId]` has one type.

A parameter or header defined by `content` is typed as a path's is (above). The client calls `paths` only (`createClient<paths>`): `webhooks` types the receiver you implement.

## Callbacks

An operation's `callbacks` are requests the API sends to a URL its runtime expression names, typed as webhooks are (above): `callbacks: { event: { "{$request.body#/callbackUrl}": { post: { requestBody: …; responses: … } } } }` in the operation's type. A Callback Object may be a `$ref` (to `components.callbacks`), and its `x-` keys are extensions, not expressions. An operation in a callback with an `operationId` is `operations[operationId]`, as a path's is.

## `$ref`

- Resolved as JSON Schema 2020-12 does: JSON Pointers, `$anchor`s and `$dynamicAnchor`s (`#node`), and the `$id`s the document declares, relative to the nearest `$id` (3.1 and 3.2), a pointer's target too: the `$ref`s in a schema reached by a pointer into a schema with `$id` resolve against that `$id`. An `$id` resolves against the schemas around it, wherever its schema is reached from, so the `$ref`s in a schema reached by a pointer to it, or by its `$id` (`schemas/inner`), resolve against its own `$id`. An `$id` that is not a URI names no resource.
- `$dynamicRef` is a `$ref`, except where it reaches a `$dynamicAnchor`: then it reaches the `$dynamicAnchor` of that name in the outermost schema resource (`$id`) the value was reached through, the document's own first (JSON Schema 2020-12's dynamic scope). That is known where the schema is used, so a component whose `$dynamicRef` reaches another `$dynamicAnchor` from there than from the document is written out there: with `Tree: { $id: tree, $dynamicAnchor: node, properties: { children: { items: { $dynamicRef: "#node" } } } }`, `StrictTree: { $id: strict-tree, $dynamicAnchor: node, $ref: tree }` is `{ children?: StrictTree[] }`, and `Tree` is `{ children?: Tree[] }`.
- Wherever this page reads a schema through its `$ref` (its target), it reads it through its `$dynamicRef` the same way, to the schema that reaches: `readOnly` / `writeOnly`, bytes, the values a property is declared with, the keys a closed object or a `oneOf` member names, the kinds a member or its target says or makes the value, the arrays a component names, and what `unevaluated*` see. Each schema reached is read in its own schema resource (`$id`).
- The document's `$self` (3.2), resolved against where it was read, is its base URI: relative `$ref`s in it resolve against `$self`, and a `$ref` to `$self` means the document (so does one to the URL it was read from). A `$self` that is not a URI reference is an error. With `$self: https://api.example.com/openapi.yaml`, `schemas/User.yaml` is `https://api.example.com/schemas/User.yaml`, which is not read (below).
- Parameters, request bodies, responses, headers, path items and media types (3.2) may be `$ref`s.
- A Path Item's fields next to its `$ref` are read with those of the Path Item it refers to, each against the document it is in: `/pets: { $ref: …, post: … }` has the referenced `get` and this `post`, and `parameters` next to `$ref` apply to both. A field in both (`summary`, `description` and extensions aside) is an error, since OpenAPI leaves which one applies undefined.
- Other files (`schemas/User.yaml`, `common.json#/Error`) resolve against the base URI where the `$ref` is: the file it is in, or the document's `$self`. Each is read once, JSON or YAML by its content, and known by where it is read: another file's `$self` is not read. URLs are not fetched.
- A schema in another file is a named type. A component that is only a `$ref` or a `$dynamicRef` to it (with at most `title` and `description`) gives the name, as it gives one to a schema it reaches that is expanded where it is used, (`User: { $ref: schemas/User.yaml }`), the first one when there are several; otherwise it is named after the file (`Order.yaml` → `Order`) or the pointer's last token (`common.json#/Error` → `Error`), numbered when taken, and listed in `schemas`.
- A component that is only a `$ref` within the document names its target the same way; other targets within the document are expanded where they are used.
- A schema may refer to itself through an object, array or tuple (`next?: Node`). One that reaches itself without one in between, through `allOf`, `oneOf`, `anyOf` and `$ref` only (`Tree: { oneOf: [{ type: string }, { $ref: Tree }] }`, `A: { $ref: A }`), is an error: TypeScript rejects `type Tree = string | Tree`. So is one that does so only in what is sent to the API (or only in what it sends), where a `readOnly` / `writeOnly` property leaves out what breaks the cycle in the other view. A schema expanded where it is used that reaches itself is named, as a schema in another file is: after the pointer's last token (`#/components/schemas/Tree/$defs/node` → `Node`), and listed in `schemas`.

## Schemas

Types follow what the schema accepts, not another generator's output.

In 3.1 and 3.2, a Schema Object is JSON Schema 2020-12, the OAS dialect. A `$schema`, or the document's `jsonSchemaDialect`, that names another dialect (`http://json-schema.org/draft-07/schema#`, 2019-09) is an error, since its keywords mean other things (draft-07's array `items`); the OAS dialect ids (`https://spec.openapis.org/oas/3.1/dialect/base`) and `https://json-schema.org/draft/2020-12/schema` are read. A 3.0 Schema Object has no `$schema`, and 3.0 no `jsonSchemaDialect`: they are not read.

## Array length

An array is `T[]` until `prefixItems`, `minItems` or `maxItems` say more; then it is a tuple.

- The first `minItems` items are required: `{ items: string, minItems: 1 }` is `[string, ...string[]]`. `prefixItems` types the first items and `items` the rest (absent, any value; `false` next to `prefixItems`, no more items): `{ prefixItems: [string], items: number, minItems: 3 }` is `[string, number, number, ...number[]]`.
- `maxItems` closes the tuple, the items past `minItems` optional: `{ minItems: 1, maxItems: 2 }` is `[T, T?]`, `{ maxItems: 3 }` is `[T?, T?, T?]`, `{ prefixItems: [string], items: number, minItems: 1, maxItems: 3 }` is `[string, number?, number?]`, `{ prefixItems: [string, number], maxItems: 1 }` is `[string?]`, and `maxItems: 0` is `[]`.
- TypeScript bounds a length only item by item, so every item is in the tuple, however many. Equal items in a row are `...repeated<[T], n>` where that is shorter than writing each, `T` written once: `{ maxItems: 1000 }` is `[...repeated<[T?], 1000>]`, the tuple of 1000 optional items. The output declares `repeated` where it uses it (see [Helper types](#helper-types)).
- `maxItems` below `minItems`, or `minItems` past `prefixItems` with `items: false`, admits no array: `never`.
- A `minItems` or `maxItems` that is not a non-negative integer is ignored.
- Arrays and tuples in `allOf` (or next to each other) meet item by item, since TypeScript reads an item of an intersection of arrays as one member's alone: `{ allOf: [{ type: array, items: string }, { minItems: 2 }] }` is `[string, string, ...string[]]`. So do the arrays in unions, member by member (`type: [string, array]` next to `oneOf: [{ type: string }, { type: array, items: string }]` is `string | string[]`), and the arrays of a property two object types share, which become one object type.
- A `$ref` to an array stays a reference, with its type beside it so that the items read as it says: `{ allOf: [{ $ref: Tags }, { maxItems: 1 }] }` is `Tags & [string?]` where `Tags` is `string[]`. Its type is read as its keywords say together: `{ type: [array, null], items: string, not: { type: null } }` is `string[]`. What it meets may admit other kinds too (`{ type: [array, null], maxItems: 1 }` is `[unknown?] | null`), and so may the schema it refers to: then its type is put beside it, and where something there admits arrays only, its arrays alone, since its other kinds meet none of it. So `{ allOf: [{ $ref: TagsOrNull }, { type: array, maxItems: 1 }] }` is `TagsOrNull & [string?]` where `TagsOrNull` is `string[] | null` (`type: [array, null]`, or `nullable: true` in 3.0), and so for members that are arrays among others (`anyOf: [{ $ref: Tags }, { enum: [""] }]`); `{ allOf: [{ $ref: TagsOrNull }, { type: [array, null], maxItems: 1 }] }` is `TagsOrNull & ([string?] | null)`, and so is `{ allOf: [{ $ref: TagsOrNull }, { maxItems: 1 }] }`, since the `type` of `TagsOrNull` says the value can be `null`, which passes `maxItems` (see [Other keywords](#other-keywords)). `const` / `enum` say so too: `{ allOf: [{ $ref: Mixed }, { maxItems: 1 }] }` with `Mixed: { enum: [[a], none] }` is `Mixed & (["a"] | "none")`. A schema is read for its arrays where it names them: by a `type` that names `array`, array keywords without `type`, `const` / `enum` with an array, a `$ref` to such a schema (another component too), or an `allOf`, `oneOf` or `anyOf` member that is one.

## Helper types

Two types say what would otherwise be written out item by item. The output declares each one where it uses it, at its end; their names are lower case, which no schema's type name is.

- `repeated<T, N>`: the items of the tuple `T`, `N` times, built ten times over for each digit of `N`: `[...repeated<[string?], 3>]` is `[string?, string?, string?]`.
- `integers<S>`: the integers whose decimal texts the template literal types `S` are: ``integers<`1${0 | 1}`>`` is `10 | 11`.

## Object types together

Object types the parts of a schema give (its own keywords, members, `if` / `then` / `else`, `dependentRequired`, …) are one object type, as TypeScript reads their intersection: each property's types met, required where one requires it, and no object where a required property admits nothing. A union of object types next to one is a union of one object type each: `{ a?: string } & ({ b: string } | { c: string })` is `{ a?: string; b: string } | { a?: string; c: string }`. Unions with one member of each kind meet kind by kind: `({ a: string } | null) & ({ a?: string; b?: string } | null)` is `{ a: string; b?: string } | null`, and `({ a: A } | "") & ("" | Record<string, unknown>)` is `{ a: A } | ""`. A union with `Record<string, unknown>` (`unknown[]`) leaves out the object (array) types beside it, which it admits. References (`Base`), index signatures and other kinds stay as they are.

## Keys

- `additionalProperties` is an index signature by any string, `[key: string]: T`. TypeScript requires it to admit every property and every other index signature's type too, so it is their union with `T` (and `undefined` for an optional property), and a key no pattern matches can have their types as well.
- A `patternProperties` pattern whose keys template literal types say (see [Values](#values)) keys an index signature by them: `{ patternProperties: { "^x-": string }, additionalProperties: false }` is ``{ [key: `x-${string}`]: string }``. A key it names (`^(a|b)$`), and each key of a template without any text, which TypeScript keys no index signature by (`^x-[ab]$`: `"x-a"`, `"x-b"`), is an optional property with the types of every pattern that matches it, `never` where they admit no value (`a?: never`, which an open object needs to reject `a`; a closed one leaves it out). A pattern every key matches (`^[\s\S]*$`, `""`) keys the index signature by any string, and `additionalProperties` applies to no key: `{ patternProperties: { "": string }, additionalProperties: false }` is `{ [key: string]: string }`. Another pattern's type joins the index signature by any string, also where `additionalProperties` is `false`; where it is a regular expression (no lookaround, word boundary, back reference or `\p{…}`) that matches every key of a template, those keys have its type too: `^x-[\s\S]+` matches every key of `` `x-a${string}` `` (and some of `` `x-${string}` ``, not `"x-"`). It is read by running a machine for each side by side, which gives up past a few thousand states; then, and where it matches only some keys (`^[a-z-]+$` and `` `x-${string}` ``), its type joins only the index signature by any string.
- A property a pattern matches has both types: `{ properties: { x-id: string }, patternProperties: { "^x-": { const: v } } }` has `"x-id"?: "v"`. So do the keys of a template that another pattern's keys include, a pattern every key matches among them, and TypeScript gives a key the types of every index signature it matches: `{ patternProperties: { "^x-a": string, "^x-": number }, additionalProperties: false }` is ``{ [key: `x-a${string}`]: never; [key: `x-${string}`]: number }``. Patterns of the same template (`^x-`, `^x-[\s\S]*`) are one index signature of both types. Next to `propertyNames: { pattern }`, a pattern's index signature is by the keys both admit, where their templates say which: by the pattern's template where `propertyNames` admits all its keys, by each `propertyNames` template within it (`{ propertyNames: { pattern: "^x-a" }, patternProperties: { "^x-": number } }` is ``{ [key: `x-a${string}`]: number }``), left out where they share none (`^y-`), and by the templates of the keys they share where they share only some, which templates always say: `^x-` and `-y$` share `"x-y"` and the keys of `` `x-${string}-y` ``. Where their templates line up in too many ways to read (thousands, with much any text), the pattern's signature stays.
- Without `additionalProperties`, the other keys have any value: an object without properties keeps `[key: string]: unknown` next to its patterns' index signatures, as `Record<string, unknown>` does.

## Values

- `const` and `enum` values the schema's keywords for their kind reject are left out: `{ type: string, enum: [a, bbb], maxLength: 2 }` is `"a"`, and a `const` they reject is `never`. Lengths count characters (`"😀"` is one), `pattern` is an ECMA-262 pattern (one JavaScript cannot read leaves out nothing), and bounds and `multipleOf` compare decimal values (`0.3` is a multiple of `0.1`), as `type: integer` reads them (`1e400` is an integer, `1e-400` is not). A `multipleOf` that is not positive is not read.
- In 3.0, `exclusiveMinimum` / `exclusiveMaximum` are booleans that make `minimum` / `maximum` exclusive; in 3.1 and 3.2 they are bounds of their own, and the tighter one applies.
- `maxLength: 0` is `""`, and `minLength` above `maxLength` is `never`.
- Bounds that admit finitely many values are those values: the integers between them for `type: integer` (`{ type: integer, minimum: 1, maximum: 5 }` is `1 | 2 | 3 | 4 | 5`, `{ minimum: 1.2, maximum: 2.5 }` is `2`), and the multiples of `multipleOf` between them (`{ type: number, minimum: 0, maximum: 1, multipleOf: 0.25 }` is `0 | 0.25 | 0.5 | 0.75 | 1`; for integers, the integers among them). Bounds that admit none are `never`, and 100,000 values or more, more than TypeScript builds into one union, are `number`. Integers in a row are spelled by their digits where that is shorter than listing each: `{ type: integer, minimum: 0, maximum: 149 }` is ``integers<`${0 | 1 | … | 9}` | `${1 | … | 9}${0 | 1 | … | 9}` | `1${0 | 1 | 2 | 3 | 4}${0 | 1 | … | 9}`>``, the same 150 numbers (see [Helper types](#helper-types)).
- `pattern` is the template literal types of the strings it matches, where they say exactly those: fixed text, sets of characters (`[a-z]`, `\d`, `\s`, `\w`), alternatives and groups, `?` and `{n}` / `{n,m}`, and any text for an end without `^` / `$` or for `*` of any character. Any character is `[^]`, or a class with a class escape and its negation (`[\s\S]`, `[\d\D]`, `[\w\W]`), whatever else it holds: `^ab[\s\S\u{10000}-\u{286A0}]*$` is `` `ab${string}` ``. `^https://` is `` `https://${string}` ``, `^v[12]$` is `` `v${"1" | "2"}` ``, `^(ab|cd)-` is `` `ab-${string}` | `cd-${string}` ``, and the values next to it are those it matches. A pattern with `.` (which does not match line breaks), `+`, `{n,}`, any character but under `*`, `*` of anything else, another negated class, `\D`, `\S` or `\W` but next to its escape in a class, a property escape (`\p{L}`), a lookaround, a word boundary or a back reference, or whose strings TypeScript would not build into one union (100,000 or more: `^[\u{10000}-\u{286A0}]$`), is `string`.
- Other lengths are `string` and other ranges `number`: `{ type: number, minimum: 0, maximum: 1 }`, and a range without one of its bounds.
- Without `type`, the keywords for strings (`pattern`, `minLength`, `maxLength`) and numbers (bounds) constrain those kinds only, and values of the other kinds the schema and the schemas it is a member of can be pass them: `{ type: string, allOf: [{ pattern: "^x-" }] }` is `` `x-${string}` ``, `{ type: integer, allOf: [{ minimum: 1, maximum: 3 }] }` is `1 | 2 | 3`, and `{ pattern: "^a$" }` alone is `"a" | number | boolean | null | unknown[] | Record<string, unknown>`.

## Other keywords

- `not: {}` (or `true`) is `never`, and `not: false` changes nothing. `not: { type }` leaves the other kinds: `{ type: [string, null], not: { type: "null" } }` is `string`; one that names a type JSON Schema does not have, which says nothing, leaves none: `not: { type: [string, file] }` is `never`. `not: { required: [a, b] }` is the objects without one of them: `{ a?: never } | { b?: never }`. `not: { not: X }` is what X admits, where its keywords say it exactly: `{}` and `true` every value, `false` none, and each of `type`, `required` (values of the other kinds pass it), `enum`, `const` and `not` (as read here) its values: `{ type: [object, null], not: { not: { type: "null" } } }` is `null`, and `not: { not: { not: X } }` is `not: X`. `not: { enum }` and `not: { const }` leave out the values they list, `boolean` being `true | false`: `{ type: boolean, not: { const: true } }` is `false`. Any other `not` and `not: { type: integer }` without `number` are ignored, with a warning: TypeScript has no type for what they leave. Nor has it one for a kind but one of its values, so a value a member may admit other than by listing it, by its kind (`type: string` for `not: { const: "" }`) or as a `$ref`, stays in that member, with a warning: on `not`, which is ignored, where it leaves out nothing, and otherwise on each such value: `{ type: [boolean, string], not: { enum: [true, a] } }` is `false | string`, with a warning on `not/enum/1`.
- `if` / `then` / `else` is `(If & Then) | (NotIf & Else)`, a missing `then` or `else` admitting anything; `if` without either asks nothing. `NotIf`, the values `if` does not admit, is what TypeScript can say of them for an `if` with `type`, `required`, `minItems`, `maxItems`, `not` and `properties` only (and annotations): the other kinds for `type` (none where it names a type JSON Schema does not have), `{ k?: never }` for each key `required` lists, the shorter arrays for `minItems` and the longer for `maxItems` (`{ type: [object, array], if: { required: [a], minItems: 1 }, then: { required: [b], maxItems: 1 } }` is `{ a: {} | null; b: {} | null } | { a?: never } | [unknown] | []`), what X admits for `not: X` (as `not: { not: X }` reads it, above), and for each property an object with it of the values its schema rejects. Those are the other kinds for a schema with `type` only, what X admits for one with `not: X` only, or, where the schema and the schemas it is a member of (through `allOf`, `$ref`, `$dynamicRef`) declare the property with a list of values (`enum`, `const`, `type: boolean` or `null`), the ones it rejects, read one by one (`type`, `const`, `enum`, lengths, `pattern`, bounds, `multipleOf`, and `not: { not: X }` as X). So `{ required: [kind], properties: { kind: { enum: [a, b] } }, if: { properties: { kind: { const: a } } }, then: { required: [x] }, else: { required: [y] } }` is `{ kind: "a"; x: string; y?: string } | { kind: "b"; x?: string; y: string }`. Any other `if`, a property of any string, or `type: integer` without `number`, is ignored, with a warning: TypeScript has no type for the values it does not admit.
- `dependentRequired: { a: [b] }` is `{ a?: never } | { b: … }`: without `a`, or with `b`. A key it lists that is left out of the view is not asked for, as `required` does not bring one back.
- `dependentSchemas: { a: S }` is `{ a?: never } | S`: without `a`, or as `S` says (`false`, without `a`; `true`, anything).
- `propertyNames` is a schema every key, a string, must meet, so the object's keys are the strings it admits, read as the schema's strings are read anywhere (`type`, `const`, `enum`, `pattern`, lengths, `not`, `allOf`, …, and through `$ref`, its target's strings rather than a named type; keywords for other kinds say nothing of them):
  - Any string (`true`, `{}`, `{ type: string }`, `{ minimum: 1 }`) asks nothing.
  - None (`false`, `{ not: {} }`, `{ type: number }`, `{ enum: [1] }`) admits no key: `{ [key: string]: never }`, `never` where a key is required.
  - Strings it names (`{ enum: [a, b] }`, `{ enum: [a, bb], maxLength: 1 }` for `a`, `{ maxLength: 0 }` for `""`, `{ pattern: "^(a|b)$" }`, and the keys of a template of its pattern without any text, `^x-[ab]$`) are the object's keys, as `additionalProperties: false` would make its properties: a listed key nothing declares has the value `patternProperties` or `additionalProperties` gives it.
  - Template literal types (`{ pattern: "^x-" }`, see [Values](#values)) key index signatures by them instead of by any string, next to the keys it names: `{ propertyNames: { pattern: "^x-" }, additionalProperties: string }` is ``{ [key: `x-${string}`]: string }``.

  A declared property it does not admit is `never` (and a required one admits no object), its own keywords deciding where they can (`{ pattern: "^x-", minLength: 4 }` leaves out `x-a`). The templates cannot carry the lengths next to them, so for the other keys those are ignored, with a warning: `{ pattern: "^x-", maxLength: 5 }` keys the object by `` `x-${string}` ``. A key the schemas that apply to the same value name, as a property or as required (its `$ref` target, `allOf` / `oneOf` / `anyOf` members, `if` / `then` / `else` and dependent schemas, and those of the schemas it is a member of, through any depth of them), is a key of the same object, so one it does not admit is `never` too: `{ type: object, properties: { a, b }, allOf: [{ propertyNames: { enum: [a] } }] }` is `{ a?: string; b?: never }`, and no object where `b` is required. Where its strings are `string` but it asks more (`{ maxLength: 3 }`, a pattern no template says), or a type that is none of these (two patterns TypeScript keeps as an intersection), it is ignored, with a warning; so is a part of it TypeScript cannot say (`not: { minLength: 2 }`), with the warning that part gives.
- `contains` asks for `minContains` (1 when not given) to `maxContains` items that match it. `minContains` above `maxContains` admits no array. Where every item matches (`contains: {}`, or an `unevaluatedItems: false` that leaves no other item; see below), every item counts, so the length is from one to the other: `{ items: string, contains: {}, maxContains: 2 }` is `[string, string?]`. With `maxContains: 0`, no item matches, so the items are what `contains` does not admit where TypeScript can say it, as for `not` (above): `{ items: { type: [string, number] }, contains: { type: string }, minContains: 0, maxContains: 0 }` is `number[]`; and where `items` lists the values (`enum`, `const`, through `$ref` and `$dynamicRef` too), the items past any `prefixItems` (whose items need not be values `items` lists) are the ones `contains` rejects, read one by one (`type`, `const`, `enum`, lengths, `pattern`, bounds, `multipleOf`, and `not: { not: X }` as X): `{ items: { enum: [a, b, c] }, contains: { const: a }, minContains: 0, maxContains: 0 }` is `("b" | "c")[]`. - `unevaluatedProperties` and `unevaluatedItems` are `additionalProperties` and `items` where no applicator (`allOf`, `oneOf`, `anyOf`, `$ref`, `$dynamicRef`, `if`, `dependentSchemas`, and for `unevaluatedItems` `contains`) is next to them, and like those say the value is an object or an array.
- Next to an applicator they see what the schema evaluates: its properties, `patternProperties` and `prefixItems`, the items its `contains` matches (none with `maxContains: 0`), those of its `$ref` target, of the schema its `$dynamicRef` reaches (its target, or the `$dynamicAnchor` the dynamic scope gives) and of its `allOf` members, each in its own schema resource (`$id`), and, where they match, those of its `oneOf` / `anyOf` members, `if` and `then` (where `if` admits the value), `else` (where it does not) and dependent schemas (where the key is present); `additionalProperties`, `items` or `unevaluated*` in any of them evaluate everything. ## `oneOf`

`oneOf` admits a value exactly one member admits. TypeScript has no type for what a member does not admit, so the members are a union, which also admits a value two of them admit, except among members that only require keys: `required`, with at most `type: object`, properties that admit any value (`{}`, `true`, a `$ref` to one) and annotations, or a `$ref` to such a schema. Such a member does not admit exactly the objects that lack one of its keys, so each of them lacks the keys the others require.

A literal or `null` two members admit is left out: `oneOf: [{ type: [string, null] }, { type: [integer, null] }]` is `string | number`, and `oneOf: [{ enum: [a, b] }, { enum: [b, c] }]` is `"a" | "c"`. Where a member admits it by its kind (`type: string` for `"a"`, `{}` for `null`), it stays: TypeScript has no type for a kind but one of its values. `boolean` is `true | false`, so `oneOf: [{ type: boolean }, { enum: [true, x] }]` is `false | "x"`. A `$ref` member is not counted.

- `oneOf: [{ required: [a] }, { required: [b] }]` is `{ a: {} | null; b?: never } | { b: {} | null; a?: never }`: `{ a, b }` is rejected.
- Lacking one of several keys: next to `{ required: [b, c] }`, `{ required: [a] }` is `{ a: {} | null; b?: never; c?: unknown } | { a: {} | null; b?: unknown; c?: never }`. The other key is declared `unknown` so that an object literal with it is not rejected as excess.
- A member that requires all of another's keys admits nothing: next to `{ required: [a] }`, `{ required: [a, b] }` is `never`.
- Other members keep their overlaps: with `{ properties: { b: { type: number } }, required: [b] }`, `{ a: 1, b: "x" }` matches only `{ required: [a] }`, so `{ required: [a] }` cannot leave out `b`, and `{ a: 1, b: 1 }`, which both match, stays admitted.

## Content by media type

| Media type                                                 | Type                                              |
| ---------------------------------------------------------- | ------------------------------------------------- |
| JSON                                                       | its schema                                        |
| `text/*`, XML                                              | `string`                                          |
| forms (`application/x-www-form-urlencoded`, `multipart/*`) | a path's response: `string`; otherwise its schema |
| `*/*`, `application/*`, which name no representation       | its schema                                        |
| any other (binary), other wildcards (`image/*`) included   | `Blob`                                            |

The client reads a sequential media type's content whole, by the rules above (`application/jsonl` is `Blob`, `text/event-stream` `string`); read it item by item with `parseAs: "stream"`. Its `itemSchema` (3.2) types each item, in `itemContent` beside `content` in the request body or response, in the view the content is in: `{ content: { "application/jsonl": Blob }; itemContent: { "application/jsonl": Event } }`.

## `nullable` (3.0)

`nullable: true` reads as OpenAPI 3.0.3 says: it adds `null` to the `type` in the same schema, and the other keywords still apply to `null`.

- `{ type: string, nullable: true }` is `string | null`.
- Without `type` it takes no effect: `{ nullable: true, allOf: [{ $ref: User }] }` is `User`.
- Next to `$ref` it is ignored, like every keyword there in 3.0: `{ $ref: User, nullable: true }` is `User`.
- An `enum` or `const` that does not list `null` keeps it out: `{ type: string, enum: [a, b], nullable: true }` is `"a" | "b"`.
- `allOf`, `oneOf` and `anyOf` members must admit `null` too: `{ type: object, nullable: true, allOf: [{ $ref: User }] }` is `User & (Record<string, unknown> | null)`, which has `null` only if `User` does, where `User` has a `type`. A member without `type` that only has object or array keywords (`{ required: [a] }`), or a `$ref` to one, does not apply to `null`, so `null` passes it (see [Other keywords](#other-keywords)).

Many documents use these forms to mean "this schema or null" (Stripe and GitHub among them), and their servers return `null`. `--loose-nullable` (`generate(src, source, { looseNullable: true })`) reads them that way: `nullable: true` adds `null` to the whole schema, next to `$ref` and without `type` too. The examples above become `string | null`, `User | null`, `User | null`, `"a" | "b" | null` and `User & Record<string, unknown> | null`.
